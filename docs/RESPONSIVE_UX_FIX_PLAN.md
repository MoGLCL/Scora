## 2. The single most important decision: one breakpoint contract

The root cause of the worst bugs is that **one decision — "is this a mobile layout or a desktop layout?" — is currently made at three different widths.**

### Current state (broken)

| Element | File | Breakpoint | Effect |
|---|---|---|---|
| Desktop nav links | `components/site-header.tsx:122` | `hidden xl:flex` | appear at **1280px** |
| Mobile bottom tabs | `components/mobile-bottom-tabs.tsx:75` | `min-[950px]:hidden` | disappear at **950px** |
| Body bottom padding | `app/layout.tsx:117` | `pb-20 lg:pb-0` | removed at **1024px** |
| Header avatar button | `components/site-header.tsx:166` | `hidden min-[950px]:flex` | appears at **950px** |

**Consequence:** between **950px and 1279px there is no navigation at all** — the bottom tabs are gone and the desktop nav has not appeared. Affected real devices: iPad Pro 11″ landscape (1194px), iPad Air landscape (1180px), iPad Mini landscape (1133px), 1024×768 laptops, and any non-maximized browser window on a 1366/1440/1536 display. Between 950–1023px there is also 80px of dead whitespace at the bottom of every page.

### Target state

**`xl` (1280px) is the one and only mobile↔desktop boundary.**

```
 0 ──────────────────────── 1279px │ 1280px ──────────────────────▶
 MOBILE / TABLET UI                │ DESKTOP UI
 • bottom tab bar (signed in)      │ • centered nav links in header
 • guest auth bar (guests)         │ • avatar dropdown in header
 • hamburger drawer (all roles)    │ • no tab bar, no drawer
 • body has pb-20                  │ • body pb-0
```

**Why `xl` and not `lg` (1024px)?** The guest nav has 7 Arabic links at `gap-7` and is absolutely centered (`absolute left-1/2 -translate-x-1/2`). Measured need is ~1100px for the links alone plus ~120px logo and ~250px auth buttons — it does not fit at 1024px and would overlap the logo. Moving the tab bar and drawer *up* to `xl` closes the gap with zero crowding risk. **Do not change the nav to `lg:flex`.**

The hamburger drawer (Task 1.2) is what gives the 640–1279px band real navigation, and is the only navigation guests have ever had on mobile.

import Link from "next/link";

  isGuest: boolean;

  const pathname = usePathname();
  const [isOpen, setIsOpen] = useState(false);

    setIsOpen(false);
  }, [pathname]);

      >
        <Menu className="h-5 w-5" />
      </button>

      {/* Backdrop */}
      {isOpen && (
        <div
          onClick={() => setIsOpen(false)}
          className="fixed inset-0 z-[60] bg-black/50 backdrop-blur-xs xl:hidden animate-in fade-in duration-200"

        dir="rtl"
        aria-hidden={!isOpen}
        className={`fixed top-0 right-0 z-[70] flex h-full w-[86%] max-w-[340px] flex-col bg-white shadow-2xl transition-transform duration-300 ease-out xl:hidden ${

      >
        {/* Panel header */}
        <div className="flex items-center justify-between border-b border-[#D1E3D6] p-4">
          <span className="font-heading text-[15px] font-black text-[#05291A]">القائمة</span>

            onClick={() => setIsOpen(false)}

                href={link.href}
                onClick={() => setIsOpen(false)}
                className={`block rounded-[14px] px-4 py-3.5 text-[14px] font-bold transition-colors ${
                  isActive
                    ? "border border-[#C5E8D1] bg-[#E8FAF0] text-[#056B38]"

## Task 1.3 — Stop iOS zoom-on-focus for all form fields

**Problem.** iOS Safari force-zooms the page whenever a focused input has a computed font-size **under 16px**, and it does not zoom back out. Every field in this app is under 16px:

| Size class on inputs | Count |
|---|---|
| `text-xs` (12px) | 67 |
| `text-[14px]` | 12 |
| `text-sm` (14px) | 9 |
| `text-[13px]` | 5 |
| `text-[12px]` | 3 |
| **16px or larger** | **0** |

Plus `app/globals.css` sets global `select { font-size: 0.8125rem; }` (13px).

This hits 144 input/textarea elements across 24 files — register, login, `complete-profile`, `complete-client-profile`, settings, `portfolio/new`, `projects/new`, support, and all admin modals. It degrades the entire signup funnel on iPhone.

**Approach: one CSS rule, not 144 edits.** Force 16px below the `sm` breakpoint only; the existing Tailwind classes keep governing ≥640px, so desktop density is untouched.

### Edit · `app/globals.css`

Append at the end of the file (after the `ssdChatPopIn` keyframes):

```css
/* ─── Mobile form fields: prevent iOS Safari zoom-on-focus ─────
   iOS zooms the viewport when a focused field computes under 16px
   and never zooms back out. Below sm we force 16px; from sm: up the
   Tailwind size utilities take over, so desktop density is unchanged.
   !important is required to beat Tailwind's utility specificity. */
@media (max-width: 639px) {
  input:not([type="checkbox"]):not([type="radio"]):not([type="range"]):not([type="color"]),
  textarea,
  select {
    font-size: 16px !important;
  }
}
```

### Notes
- Scoped to `max-width: 639px`, so it can never affect desktop.
- The `:not(...)` chain keeps checkbox/radio/range/color controls from being resized.
- This also overrides the 13px global `select` rule on mobile, which is intended.
- Fields with a fixed height (`h-12`, `h-[52px]`) have enough room for 16px text — verify visually, but no height changes are expected.

### Acceptance criteria
- On a real iPhone or Safari's iOS simulator at 390px: tapping into every field on `/register`, `/login`, `/settings`, `/projects/new` produces **no zoom**.
- At 1024px+ the fields look identical to before the change (compare screenshots).

## Task 2.2 — `100vh` → `dvh` migration

**Problem.** 32 uses of `min-h-screen` / `100vh`, zero `dvh`. On mobile Safari and Chrome, `100vh` includes the retracted URL bar, so full-height sections are taller than the visible area — bottom content is clipped and the layout jumps as the bar collapses.

Tailwind 4.3.3 ships `min-h-dvh` / `h-dvh` (verified against the installed package).

npx tsc --noEmit

## Task 3.6 — Raise the small-type floor

**Problem.** 360 instances of sub-12px text — `text-[11px]` ×228, `text-[10px]` ×113, `text-[9px]` ×19 — against only 31 responsive font-size declarations in the entire app. Arabic script carries diacritics and denser letterforms, so it needs more optical size than Latin at the same px; 10px Arabic on a phone is unreadable for many users over ~35.

This is the largest-volume item here and the most subjective, so **do it last and incrementally** — a blind global replace will break dense admin tables and badge layouts.

Suggested policy:

| Current | Target | Scope |
|---|---|---|
| `text-[9px]` | `text-[11px]` | everywhere (19 sites — no real use case for 9px) |
| `text-[10px]` | `text-[11px] sm:text-[10px]` | badges/pills only, where density matters at desktop |
| `text-[11px]` on body copy, labels, metadata | `text-[12px]` | reader-facing text |
| `text-[11px]` inside dense admin tables | leave | desktop-only surface |

Start with the highest-traffic reader-facing surfaces and verify each visually:
1. `app/profile/[username]/page.tsx` (metric banners, badges)
2. `app/developers/developers-client.tsx` (result cards)
3. `app/projects/projects-client.tsx` (project cards)
4. `app/dashboard/page.tsx` (stat tiles)
5. `components/site-footer.tsx` (12px already — fine)
